# Decisions

Engineering decisions inside the stack. One line each: date, decision, reason. Methodology decisions go through `/decision`, not here.

- 2026-10-06: Local Postgres on host port 5440 and Redis on 6390 in `docker-compose.yml`. Avoids clashing with common local services on 5432 and 6379/6380.
- 2026-10-06: Tests create a throwaway database `innovaluation_test_<random>` on `TEST_DATABASE_URL`'s server, migrate it with Alembic, and drop it after the run. Each test runs in a rolled-back transaction. Matches the project rule of a throwaway Postgres database per test run.
- 2026-10-06: `tests/scoring` never touches the database fixtures, so `bin/test-scoring` runs without Postgres and stays fast.
- 2026-10-06: Errors use one `AppError(code, message, status_code)` class; HTTP, validation and unhandled errors map into the same `{"error": {...}}` envelope in one module.
- 2026-10-06: SQLAlchemy metadata uses a constraint naming convention so Alembic names stay stable across autogenerate runs.
- 2026-10-06: `config/ai.yml` defaults to `claude-sonnet-5-5`, with `claude-opus-5-5` for `propose_iq_scores` and `report_narrative` (the highest-stakes outputs). Tunable per touchpoint without code changes.
- 2026-10-06: CI is GitHub Actions with two jobs (backend: ruff, format, mypy, scoring tests, pytest with a Postgres service; frontend: lint, typecheck, vitest, build). Redis is not needed in CI because Celery runs eagerly in tests.
- 2026-10-06: Frontend on Next 16 + React 19 + Tailwind 4 + Vitest 4; `engines.node >= 20.19` because Vite 8 and jsdom 29 need it.
- 2026-10-06: `npm run typecheck` runs `next typegen` before `tsc --noEmit`, since Next 16 route types are generated.
- 2026-10-06: The assistant note files that create-next-app adds to `frontend/` are kept local and ignored by git; `next dev` re-creates them.
- 2026-10-06: Validation error responses strip submitted `input` and `ctx`, so user text never echoes into responses or logs.
- 2026-10-06: Frontend API types are hand-written for Phase 0 (one endpoint). Switch to `openapi-typescript` generated from `/openapi.json`, with a CI drift check, in Phase 2 when the API grows.
- 2026-10-06: CI uses Node 22 LTS (Node 20 is end of life); local `engines` stays `>=20.19` so both work.
- 2026-10-06: Docker Postgres and Redis publish on 127.0.0.1 only; dev credentials are weak and Redis has no auth.
- 2026-10-06: Unhandled exceptions become the 500 envelope in an ASGI middleware inside CORS, so browsers can read `internal_error`.
- 2026-10-06: Settings refuse to start in staging or production with the default or a short `SECRET_KEY`.
- 2026-10-06: Git hooks live in `.githooks/` (enabled by `bin/setup` through `core.hooksPath`), with all logic in `bin/check` so hooks, humans and CI share one definition. No hook framework dependency.

- 2026-10-06: Dependency audits block on production dependencies only (`pip-audit` on the locked set, `npm audit --omit=dev --audit-level=high`). The 5 known high findings are in dev-only lint tooling.
- 2026-10-06: Commit subjects are limited to 100 characters (commitlint default); the push scan skips commits already on `main`.

Weights are int or Decimal only (floats change IQs through binary rounding); error messages show caller values through `describe()`, which never raises. YAML loads with a libyaml `CSafeLoader` subclass when available (pure `SafeLoader` fallback), both rejecting duplicate keys.

- 2026-10-12: Frontend API types are generated with `openapi-typescript` (pinned) into `frontend/src/lib/api/schema.d.ts` and replace the hand-written ones. The committed `frontend/openapi.json` (from `uv run python -m app.openapi_dump`) is the contract; CI and `bin/check full` fail if the backend schema or the generated types drift from it. The error envelope stays hand-written in `types.ts` until a route declares it.
- 2026-10-12: Platform admin (tech admin) is a user-level flag (`users.is_platform_admin`), not an organisation role, because platform staff span organisations. Membership roles are `owner`, `admin`, `member`, `committee`, `investor` only.
- 2026-10-12: A consultant is never a membership. Consultant access is only through `consultant_grants`, with a required end date (`expires_at`) that the client chooses (Q12).
- 2026-10-12: Invitation, email verification and password reset tokens are stored only as SHA-256 hex digests. The raw token exists only in the email link, so a database leak exposes no usable token.
- 2026-10-12: Primary keys are UUIDs, so record IDs in URLs cannot be guessed or counted.
- 2026-10-12: Enumerations (roles, statuses, token purposes, grant scopes) are VARCHAR plus one named CHECK constraint, not native Postgres enums, so adding a value is a constraint swap in a migration.
- 2026-10-12: Audit events RESTRICT organisation deletes and SET NULL their actor on user deletes. Organisations are archived, not deleted; a deliberate erase must remove the audit events first.
- 2026-10-12: Celery `result_expires` is one hour. Task results can hold user text and must not stay in Redis; durable outputs live in Postgres (`AiRun` and the result tables).
- 2026-10-13: Passwords use `argon2-cffi` directly (argon2id, library defaults, RFC 9106 low-memory profile). Sign-in re-hashes when `check_needs_rehash` reports old parameters. Unknown emails and Google-only users are verified against a dummy hash so timing does not reveal accounts. Length 10 to 128 characters, never trimmed.
- 2026-10-13: The session is a PyJWT HS256 token in the httpOnly `iv_session` cookie (`SameSite=Lax`, `Path=/`, `Secure` in staging and production; see the `__Host-` entry below for deployed names), with a fixed 7-day lifetime (`SESSION_LIFETIME_DAYS`). Claims: user id, `session_version`, CSRF token, active organisation id. Switching organisation re-issues the cookie but keeps the original end time.
- 2026-10-13: `users.session_version` (migration `0003_auth`) is checked on every request. Password change, password reset and account disable raise it, ending every session of that user. Sign-out clears this browser's cookies only; a "sign out everywhere" button would just raise the version.
- 2026-10-13: Keys for the session JWT, the email tokens and the sign-in throttle are each derived from `SECRET_KEY` with HMAC and a fixed label, so one use cannot be replayed as another.
- 2026-10-13: CSRF is a signed double submit: the readable `csrf_token` cookie must equal the `X-CSRF-Token` header and the token inside the signed session, on every POST, PUT, PATCH and DELETE with a session. A planted cookie fails. Every unsafe request is also rejected when `Origin` is not the frontend origin (or `Sec-Fetch-Site` is `cross-site`), which covers sign up, sign in, verify and reset, which have no session yet.
- 2026-10-13: CORS allows only `GET`, `POST`, `PATCH` and the headers `Content-Type` and `X-CSRF-Token`. A test fails when a route uses a method not in the list (add `DELETE` with the first route that needs it).
- 2026-10-13: Sign-in throttling lives in Postgres (`sign_in_throttles`), not Redis, so it works in CI and tests. It counts failures per HMAC of the normalised email, whether or not an account exists: 5 failures in 15 minutes lock that email for 15 minutes with 429 `too_many_attempts`, the same for real and unknown emails, so a lock reveals nothing. Success and password reset clear it. Pruning of old rows is left for a periodic task.
- 2026-10-13: Email verification and reset tokens are never passed to Celery. The raw token is an HMAC of the `user_tokens` row id under a key derived from `SECRET_KEY`; the database stores its SHA-256 hash. The email task receives only ids and rebuilds the link, so the broker never holds a usable token and a database leak alone reveals none. Rotating `SECRET_KEY` voids outstanding links (it also ends sessions).
- 2026-10-13: Issuing a verification or reset token voids the user's older tokens of the same purpose (only the newest link works), and at most one is issued per user per minute. Using one marks it and the rest used. Reset links last 1 hour, verification links 24 hours. A successful reset also marks the email verified, since the link proves the inbox.
- 2026-10-13: No account enumeration: sign up, resend verification and forgot password always answer 202 with the same message. Sign up with a verified email changes nothing and sends at most one "you already have an account" email per hour (the email task re-checks that audit event). Sign up with an unverified email is covered by the pre-registration entry below. `email_not_verified` and `account_disabled` are returned only after the right password.
- 2026-10-13: Email sending: Resend (`resend` SDK) when `RESEND_API_KEY` is set, with the reference id as Resend's idempotency key so a re-delivered task does not send twice. Without a key, development and test log the recipient, subject and link at INFO; staging and production fail the task with `EmailNotConfiguredError` (and log an error at startup) instead of dropping the email. Templates are Jinja2 HTML plus plain text in `app/emails/templates/`.
- 2026-10-13: Celery tasks open their database session through `app.jobs.db.task_session()`. Tests point it at the per-test session, so eager tasks see the rows the request just wrote inside the rolled-back transaction.
- 2026-10-13: Request emails are validated with Pydantic `EmailStr` (`email-validator`, no DNS lookups), then normalised with `normalise_email`. Request bodies reject unknown fields.
- 2026-10-13: Permissions live in one table (`ROLE_PERMISSIONS` in `app/core/permissions.py`), mirrored in `docs/architecture/permissions.md` and checked by a test. Routes use `require_permission(...)` (or `require_role(...)`). `current_org` returns an `OrgContext` (organisation, user, role) and re-checks the membership or a live consultant grant on every request; the consultant lookup is already in `resolve_org_access`, so granting access needs no change at call sites.
- 2026-10-13: The active organisation is a session claim chosen with `POST /me/active-organisation`. At sign-in it is set automatically only when the user belongs to exactly one organisation. No active organisation gives 409 `no_active_organisation`; lost access gives 404 `not_found`.
- 2026-10-13: Terms version is one setting, `TERMS_VERSION` (default `2026-10-13`), stored on each new account with the time of acceptance. Change it when the terms text changes.
- 2026-10-13: Email and password sign-in is behind `PASSWORD_SIGN_IN_ENABLED` in `app/services/auth.py`, marked PROVISIONAL for open-questions Q14 (default "both").
- 2026-10-13: Pre-registration takeover fix (migration `0004_auth_hardening`): a repeat sign-up for an email whose account is not verified yet never carries a password and changes nothing on the account. Its verification link is marked `user_tokens.requires_password`; using it needs a new password in the same request (400 `password_required` without one, and the link stays usable), and that password replaces whatever the account had. Once any link of an account required a password, every later one does too (resend included) until the email is verified. Verifying raises `session_version`, clears the sign-in lock and voids other links. A first sign-up's link stays one click and keeps the sign-up password (a password sent with it is ignored). The response to a repeat sign-up is identical to a new one. Only the newest link works; repeat sign-ups skip the one-minute cooldown but are capped at 5 links per hour. Result: whoever signs up first or last, only someone who reads the inbox sets the password that survives verification. Thursday's `/verify-email` page shows a "choose your password" field when it gets `password_required` and resubmits with `password`.
- 2026-10-13: For Friday: Google sign-in that claims an existing unverified account must clear `password_hash`, void outstanding verification tokens and raise `session_version`, so a password set by whoever signed up before cannot survive.
- 2026-10-13: Sign-in throttling counts the attempt before checking the password: `SELECT ... FOR UPDATE` on the throttle row, refuse if locked or if the 15-minute window already holds 5 attempts, commit (releasing the lock before the slow argon2 check), then verify; a wrong password locks the email once the window is full, the right one deletes the row. Parallel guesses cannot pass the limit (tested with 20 threads on separate sessions). Columns renamed to `attempt_count` and `window_started_at`.
- 2026-10-13: Per-IP rate limiting on `/api/v1/auth/*` is deferred to Phase 8 (edge proxy or Redis), but it must exist before any public staging site goes live. The per-email throttle alone does not stop one client spraying many emails.
- 2026-10-13: In staging and production the cookies are `__Host-iv_session` and `__Host-csrf_token` (Secure, `Path=/`, no `Domain`), so a sibling subdomain or plain http cannot set or overwrite them. Locally the plain names `iv_session` and `csrf_token` are used, because browsers reject `__Host-` cookies over http. The frontend reads whichever CSRF cookie exists.
- 2026-10-13: Email links carry the token in the URL fragment (`/verify-email#token=...`, `/reset-password#token=...`), which browsers never send to a server, so tokens stay out of access logs, proxies and Referer headers. Thursday's frontend pages read `location.hash`, POST the token, then clear the hash with `history.replaceState`.
- 2026-10-13: Audit flood control: a failed sign-in for an unknown email writes no audit row; a known account gets one row per wrong password (bounded by the throttle) and one `locked` row when a lock starts, not one per refused attempt. Sign-in audit rows hold the reason only; the actor id identifies the account, so no email is stored.
- 2026-10-13: Resend verification and forgot password do the same work in the request for every email: one indexed lookup, a commit and one queued `emails.request_account_email` task (with the user id, or none for an unknown email). Issuing the token, auditing and sending happen in the worker, so response time does not reveal registered emails. A re-delivered task hits the per-user rate limit and sends nothing more; a crash between issuing and sending loses that email, and the user can ask again after a minute.
- 2026-10-13: Archived organisations are view-only until the archive feature exists (Phase 8 admin panel): they cannot be chosen as the active organisation (409 `organisation_archived`), are not picked automatically at sign-in, and every permission except viewing is refused (403 `organisation_archived`). `/me` memberships include `organisation_status` so the UI can show this.
- 2026-10-13: Sign-out always clears the cookies, even when the CSRF check fails, but it is audited (counted as the user's own action) only with a valid session and a passing check. `/me` returns `active_organisation_id: null` when the session's organisation is no longer reachable.
- 2026-10-13: `disable_user` (in `app/services/users.py`, for the Phase 8 admin panel) sets `is_active` false, raises `session_version` and writes a `user.disabled` audit event; re-enabling the account later does not revive old sessions.
- 2026-10-13: The consultant grant lookup requires `scope = read_results`; a future scope must decide its own role before it grants access.
- 2026-10-13: Settings refuse a `FRONTEND_ORIGIN` in staging or production that is not https, is localhost or a loopback address, or has a path, query or fragment. It is the only origin allowed to make unsafe requests and the base of every email link.
- 2026-10-15: Any signed-in, verified user may create an organisation (`POST /organisations`) and becomes its owner; it becomes their active organisation. Abuse limit: 10 new organisations per user per day.
- 2026-10-15: Team rules: only an owner gives the owner role or changes or removes an owner; the last owner cannot be demoted or removed. Every team change locks the organisation row and re-reads the actor's role. See `docs/architecture/permissions.md`.
- 2026-10-15: Invitations last 7 days (product setting `INVITATION_LIFETIME`). Inviting the same email again replaces the old link, so "resend" is inviting again. The token is an HMAC of the invitation id under its own key, sent in the URL fragment (`/invitations/accept#token=...`). `POST /invitations/preview` shows the organisation, role and invited email without a session; `POST /invitations/accept` needs a signed-in, verified account with the invited email (403 `invitation_email_mismatch` otherwise), so a forwarded link is useless to anyone else. Abuse limits: 50 invitations per organisation per day, 100 per person per day across organisations, 3 per (organisation, email) per hour.
- 2026-10-15: Consultant access (Q12): the owner or admin gives access to an email with an end date (any future date the client chooses; the only ceiling is technical, 100 years ahead, because Postgres stores dates near year 10000 that the driver cannot read back), can move the end date or revoke. The consultant accepts on their own access page while signed in with a verified account for that email; the email carries no token. One open grant per (organisation, email); members cannot also be consultants. Accepted, live grants appear in `/me` as `consultant_organisations` for the switcher. End dates are stored in UTC. Abuse limits: 20 grants per organisation per day, 40 per person per day across organisations.
- 2026-10-15: Team email subjects are fixed text; the organisation and person names typed by users appear only in the body, escaped in HTML. The email task gets ids only and re-checks that the invitation is pending, or the grant still waiting, and that the organisation is not archived.
- 2026-10-15: CORS now allows `DELETE` (removing a member, cancelling an invitation, revoking consultant access).
- 2026-10-15: Team locks are always taken in one order: the organisation row first, then the invitation or grant row, re-read under the lock (`populate_existing`). Inviting, cancelling and accepting therefore cannot deadlock or overtake each other; a cancel that loses to an accept answers 404. Role lookups always re-read from the database.
- 2026-10-15: An invitation counts only while its sender may still give its role (still an owner or admin; still an owner for owner invitations). Joining by invitation revokes the person's open consultant access to that organisation (audited, reason `became_member`), so removing them later leaves no access behind.
- 2026-10-15: Accepted risks: organisation and person names are free text in team emails (fixed subjects, escaped HTML and the rate limits above keep the abuse small); the organisation creation limit is counted without a lock, so parallel requests can pass it by a few. Revisit both with the Phase 8 security review.
- 2026-10-16: Google sign-in is out of the MVP (Haroon's call on the P2.02 card: email and password is enough, add it later if Amy wants it). The user model keeps `sign_in_method` and `PASSWORD_SIGN_IN_ENABLED` stays PROVISIONAL for Q14, so adding it later needs no migration. IN.01 therefore only owes the email sending key (Resend) before Amy's demo; unset, emails are logged instead of sent.
- 2026-10-16: Dates anchored to a UTC calendar day (consultant end dates, invitation expiry, joined dates) are shown in UTC everywhere, so the date an admin picks is the date everyone sees. The frontend formats them with `timeZone: "UTC"` in `frontend/src/lib/format.ts`.
- 2026-10-17: Provisional brand (Q17, pending Amy's approval): the ice-blue and emerald palette and type proposed from the compass mark, as the prototype's final stylesheet renders it. Tokens live in `frontend/src/app/globals.css` (primary blue darkened slightly for AA contrast on buttons); headings use Playfair Display, body Plus Jakarta Sans, both self-hosted through next/font; the compass mark is the header logo and app icon. - 2026-10-17: New-password policy, NIST SP 800-63B style: 10 to 128 characters, every character allowed, deliberately no composition rules; a new password is refused with 422 `weak_password` when it is on the UK NCSC 100k most-used-passwords list (shipped as `backend/app/core/common_passwords.txt`, filtered to the entries that pass the length rule) or contains the holder's email local part, a word of their name (4+ letters) or the product name. The check runs wherever a password is set (sign-up, choose-a-password links, reset, change), before a link is consumed (a refused password keeps the link usable) and before the throttle counts an attempt; at sign-up it depends only on the submitted values, so it reveals nothing about existing accounts. A live Have I Been Pwned range check can replace the static list in Phase 8.
- 2026-10-17 (amended): the password minimum is 8 characters, NIST's floor (was 10). The common-password list is refiltered to 8 to 128 characters (46,483 entries), so the shorter breached passwords it now admits by length are still refused by the list. The length message appears only while the typed password is under 8; there is no standing hint.
- 2026-10-19: Development emails go to Mailpit (`axllent/mailpit`, in docker-compose: inbox http://localhost:8025, SMTP `localhost:1026`) through `DevSmtpEmailBackend` (stdlib `smtplib`, settings `DEV_SMTP_HOST` and `DEV_SMTP_PORT`), as a multipart message with the plain text and the HTML. The backend still writes the log line first, and a stopped Mailpit only logs a warning, so a developer always has the link. It inherits the log backend's refusal to run deployed. Test keeps the log backend, and the test suite uses the in-memory outbox. Email templates stay Jinja2 (tables and inline styles, in the provisional brand); no MJML build step.
- 2026-10-19: Letter-opener behaviour in development: after delivering to Mailpit, `DevSmtpEmailBackend` finds the email by its own Message-ID through Mailpit's search API and opens `/view/<id>` in a new browser tab (`webbrowser.open_new_tab`, on the machine running the worker). On by default; `DEV_EMAIL_OPEN_BROWSER=false` turns it off. Any failure (no browser, Mailpit unreachable) is swallowed at debug level, since the log line and the inbox still hold the email. An autouse test fixture makes any attempt to open a browser fail the test.
- 2026-10-19: The currency setting is a searchable select (`CurrencySelect`, on Headless UI's Combobox, `@headlessui/react` pinned to 2.2.10). The list comes from the runtime's ISO 4217 data (`Intl.supportedValuesOf("currency")` with `Intl.DisplayNames` for English names), minus XDR, XSU and XXX, so there is no currency list to maintain. Search matches codes first, then names. The backend still only checks the 3-letter shape.
- 2026-10-21: Readiness assessment flow (P3.02 to P3.04, `app/services/readiness.py`, `/api/v1/readiness`). An owner or admin starts an assessment (one open per organisation; 409 `assessment_open`), which goes straight to `collecting` (`draft` is reserved). Everyone who may answer (owner, admin, member, committee) saves their own answers as they go (PATCH merges; null clears; answers are strict integers, so "3" and true are refused) and submits once all 60 are answered (spec 2.8). The facilitator (owner or admin) then starts consensus, which closes answering; people who never submitted are left out. The facilitator sees each submitted answer by name, the mean (2 decimals, halves up like the engine) and the spread, and sets the agreed answer and an optional note per question. Finalising needs all 60 agreed answers (spec 2.7), scores them with the engine only, writes the result once and makes the assessment immutable. Individual answers are shown to the facilitator only; members see their own answers and final results; consultants see final results only. PROVISIONAL display-only defaults that change no number: a question is highlighted for discussion when its spread is 2 or more, and the result calls the 3 highest dimensions strengths.
- 2026-10-21: A result's strengths are the highest-scoring dimensions that score above every priority (up to 3), so no dimension is ever both a strength and a priority; when everything ties, none is shown. PROVISIONAL display choice, no number changes.
